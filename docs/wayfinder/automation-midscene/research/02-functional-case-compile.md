# 功能用例 → Midscene AI 指令编译策略调研

## 结论先行

**推荐 B（LLM 预编译）为主、A（逐条直映）为可选降级路径。** 对现有 115 条真实功能用例的统计显示：23% 的用例含合并操作步骤、66 条预期结果含"成功/正常"类模糊谓词、38% 含浏览器内不可执行的后端操作、且步骤文本存在两种换行形态（字面 `\n` 序列 95 条 / 真实换行 20 条）。直接把步骤文本逐条喂给 `aiAct` 的失败面太大；先用廉价文本 LLM 把用例编译成"原子动作 + 可视觉断言 + 手工项标注"的结构化指令序列，可以消解上述大部分风险，且编译结果可按用例缓存，重复执行零额外成本。

## 1. 数据结构与文本形态

### 1.1 数据结构（server/src/features/testcase/）

`TestCaseRecord`（types.ts:39-52）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `caseId` / `module` / `testPoint` / `title` / `priority` | string | 编号、模块、测试点、标题、优先级 |
| `precondition` | **string（单段文本）** | 前置条件，常为 `；` 分隔的多条件并列 |
| `steps` | **string（单段文本）** | 测试步骤，`1. 2. 3.` 编号列表，**不是结构化数组** |
| `expectedResult` | **string（单段文本）** | 预期结果，与步骤编号一一对应（生成 prompt 强制约束） |
| `row` | string[] | 上述 8 列的 CSV 行镜像（导出/表格展示用） |

持久化（mysql-persistence.ts:51-64）：`precondition` / `steps` / `expected_result` 均为 `MEDIUMTEXT` 列，无步骤级结构。执行结果回写位已存在：`TestSetRecord.executionStatus: Record<caseId, {status: untested|passed|failed|blocked, note, updatedAt}>`（types.ts:3-8, 33），「执行」按钮的结果可直接落在该结构上。

生成侧约束（prompts.ts:28, 45, 192-193）：两套 system prompt 都强制"步骤与预期结果必须 1. 2. 3. 编号且一一对应、禁止'正常/符合预期'等模糊表述、预期必须具体可断言"。**实际产出并未完全遵守"禁模糊"约束**（见 §1.3 统计）。

### 1.2 真实文本形态（抽样自 MySQL，共 2 个功能用例集 115 条）

用例集：`登录`（20 条）、`包年套餐与阶梯计费需求分析`（95 条），均为 AI 生成的 functional/zh 用例。

**样例 1 —— TC001（登录集，换行为真实 `\n`）：**

```
[前置条件] 账号user_normal已注册且处于正常激活状态
[测试步骤] 1. 访问系统登录页面
2. 在账号输入框输入user_normal
3. 在密码输入框输入正确密码ValidPass123
4. 点击【登录】按钮
[预期结果] 1. 登录页面正常加载，输入控件可用
2. 账号输入框正常显示输入的user_normal
3. 密码输入框以掩码形式展示输入内容
4. 登录成功，系统自动跳转至系统首页并展示当前用户登录态与昵称
```

**样例 2 —— TC040（套餐集，换行为字面 `\n` 两字符序列，含后端操作）：**

```
[前置条件] 阶梯套餐PKG-O已生效，最高档上限500000条；OPS超量单条价0.05元/条已配置；全年累计已达500000条
[测试步骤] 1.确认累计用量500000条\n2.再发起20000条调用使累计达520000条\n3.触发结算\n4.查看账单构成
[预期结果] 1.累计确认50万条\n2.累计达52万条\n3.结算完成\n4.50万条以内按最高档包年价结算，超出2万条按单条计费=20000×0.05=1000.00元
```

**样例 3 —— TC010（套餐集，含"记录 ID 供后续步骤用"的数据依赖）：**

```
[测试步骤] 1.按OPS+OP顺序提交创建套餐\n2.保存成功后记录套餐ID\n3.按OP+OPS顺序再次提交相同价格限量配置\n4.查看系统处理结果
[预期结果] ...4.系统提示组合已存在或幂等返回原套餐，不生成两套冲突计费规则
```

**对照：zentao 导入的传统手写用例**（TestCase/zentao/智信学习-所有用例.csv）粒度远更粗——`1.执行页面展示与文案校验 2.观察页面反馈与数据变化`，预期写`实际结果符合预期`。这类用例任何策略都无法直接自动执行，仅作对照，不是本次抽样的主数据源。

### 1.3 全量统计（115 条，归一化换行后）

| 维度 | 数值 | 对执行的影响 |
|---|---|---|
| 步骤为编号列表 | 100%（平均 4.0 步 / 4.0 预期，编号数不一致 0%） | 编号对应关系可靠，可按 (step_i, expected_i) 配对 |
| 换行形态 | 字面 `\n` 序列 **95 条** / 真实换行 **20 条** / 单行 0 | **喂给 aiAct 前必须统一归一化**（csv.ts:64 已有同款 `replace(/\\n/g,"\n")` 处理） |
| 含合并操作词的步骤（并/同时/然后/，） | 23% | 单步多动作，直映 aiAct 易只执行前半 |
| 预期含模糊谓词 | "成功" 66 条、"正常" 26 条、"正确" 14 条 | 多数与具体可观察点同句（如"保存成功生成套餐ID"），纯模糊不可判的是少数 |
| 预期含具体数值断言 | 44%（51 条） | 数值断言可被 aiAssert 视觉判定，但要防止 VLM 算错账 |
| 单条预期含多断言子句 | 59% | 整体 aiAssert 会因部分满足而误判，需拆分 |
| 含后端/非 UI 操作（触发结算、发起 N 条调用、看日志、落库、抓包、断网） | **38%（44 条；套餐集 39/95=41%）** | 浏览器 UI 自动化**天然做不了**，直映会在页面上乱找乱点产生假失败 |
| 含具体测试数据 | 77%；占位/任意类变量仅 4% | 数据内联度高，aiAct 可直接用；变量化收益小但可做 |
| 步骤含 UI 名词（页面/按钮/输入框/勾选/点击） | 33%（登录集高、套餐集低） | 套餐集大量步骤是业务语言而非 UI 语言（"配置包年价""触发结算"），需要编译层补 UI 语义 |
| 步骤/前置中含 URL | **0%** | 入口地址必须由外部（项目/环境配置）注入，两种策略都绕不开 |
| 前置条件为多条件并列 | 64% | 前置多为数据态（"套餐PKG-O已生效""累计已达500000条"），浏览器内无法准备，需标注为外部数据准备依赖 |

## 2. 策略对比

| 维度 | A. 逐条直映（步→aiAct，预期→aiAssert） | B. LLM 预编译（文本 LLM → 结构化指令 → 执行） |
|---|---|---|
| 额外成本 | 零（但每条用例 ~8 次 VLM 调用照付） | 每用例 1 次文本 LLM 调用（无视觉，便宜），编译结果可按用例 version 缓存，改例才重编 |
| 合并操作步骤（23%） | 直接失败面：aiAct 对"输入X并点击Y"类复合指令常只做一半 | 编译期拆成原子动作，消解 |
| 伪装成动作的断言步（如"确认累计用量""查看账单构成"） | aiAct 会试图"操作"一个验证动作，行为不可预期 | 编译期改判为 assert/extract，各归其位 |
| 后端/非 UI 操作（38%） | **最大失败源**：在页面上找不存在的入口 → 超时 + 假失败 | 编译期标注 `manual/blocked + 原因`，执行器跳过并如实上报，用例评为 partial |
| 模糊谓词（66 条含"成功/正常"） | aiAssert 直接判"登录成功"尚可，判"页面反馈与业务预期一致"必幻觉或恒 pass | 编译期把模糊谓词绑定到同句的具体可观察点（"生成套餐ID""跳转首页"），无法绑定的标注"断言不可判，需人工" |
| 多断言子句（59%） | 整体断言部分满足 → 误判 pass/fail | 编译期拆成独立断言，逐条判定 |
| 数据依赖（"记录套餐ID"后续引用） | 无法支持，步骤间状态丢失 | 编译期生成 extract + 变量引用（`{{packageId}}`），执行期串联 |
| 换行/编号噪声（95+20 两种形态） | 字面 `\n` 直接进 prompt，干扰定位 | 编译输入前统一归一化（确定性代码做，不靠 LLM） |
| 幻觉风险 | VLM 在执行现场幻觉（判错） | LLM 在编译期幻觉（编造步骤/元素）——可用 schema 校验 + fromStep 溯源字段 + 与原文 diff 兜底 |
| 可解释/可调试 | 失败时只有"aiAct 某步失败" | 编译产物人可读，执行前可预览、可手工修正后执行 |
| 适配 zentao 类粗粒度老用例 | 完全不可行 | 可编译出"全 manual + 原因"，至少给出如实反馈 |

**小结**：A 的失败不是边缘案例而是主路径风险——38% 后端操作 + 23% 合并步骤 + 59% 多断言子句，且这些用例集（套餐计费类）正是回归测试的主力。B 用一次廉价文本调用把"自然语言用例"与"Midscene 可执行指令"解耦，还能产出缓存、溯源、手工项标注三个副产品。

## 3. 推荐方案与预编译 prompt 草案

### 3.1 推荐架构

```
用例(steps/expectedResult 原文)
  → [确定性预处理] 换行归一化、编号切分（复用 csv.ts 的 \n 处理逻辑）
  → [文本 LLM 编译]  → CompiledPlan(JSON，按 caseId+文本hash 缓存)
  → [执行器] 逐条映射：act→aiAct / assert→aiAssert / wait→aiWaitFor / extract→aiQuery+变量表
             manual→跳过并记入报告
  → 结果聚合回写 executionStatus（passed/failed/blocked，manual 项记 note）
```

A 模式保留为"快速试跑"开关（单步调试时直映原文，便于对照编译产物是否正确）。

### 3.2 预编译 prompt 设计草案

**输入**（user message，JSON）：

```json
{
  "case": {
    "caseId": "TC040",
    "title": "[P0]实际用量52万超过最高档上限50万时超出2万条按单条计费",
    "precondition": "阶梯套餐PKG-O已生效；……",
    "steps": ["1.确认累计用量500000条", "2.再发起20000条调用……", "…"],
    "expected": ["1.累计确认50万条", "…"]
  },
  "env": {
    "entryUrl": "https://example.com/billing",
    "appBrief": "SaaS 计费管理后台，左侧导航含【套餐管理】【账单中心】",
    "variables": { "operator": "sales_01" }
  }
}
```

`entryUrl` / `appBrief` 来自项目级配置（用例文本 0% 含 URL，必须外部注入）；`appBrief` 给编译器页面结构先验，降低编造导航路径的概率。

**输出 schema**（严格 JSON，禁止 markdown 围栏）：

```json
{
  "caseId": "TC040",
  "executable": "full | partial | manual",
  "variables": [
    { "name": "packageId", "value": null, "source": "extract", "fromStep": 2 }
  ],
  "setup": [
    { "type": "navigate", "url": "{{entryUrl}}" },
    { "type": "external", "text": "确保套餐PKG-O已生效且累计用量已达500000条", "reason": "数据态前置，浏览器内无法准备" }
  ],
  "instructions": [
    { "id": 1, "type": "act", "text": "在左侧导航点击【账单中心】", "fromStep": 1 },
    { "id": 2, "type": "assert", "text": "用量概览区显示累计用量为 500000 条", "fromStep": 1, "fromExpected": 1 },
    { "id": 3, "type": "extract", "text": "读取当前累计用量数值", "saveAs": "usageBefore", "fromStep": 1 },
    { "id": 4, "type": "wait", "text": "等待账单页面加载完成", "fromStep": 4 }
  ],
  "manualItems": [
    { "text": "再发起20000条调用使累计达520000条", "fromStep": 2, "reason": "需通过 API/压测工具发起调用，非 UI 操作" },
    { "text": "触发结算", "fromStep": 3, "reason": "后端批处理动作，UI 无入口" }
  ],
  "compileNotes": ["预期第4条含两个断言子句，已拆分为 id=5,6 两条独立断言"]
}
```

**关键约束（system prompt 核心条款）：**

1. **不改语义**：只重组、拆分、改写，不新增原文没有的操作或断言；每个输出指令必须带 `fromStep`/`fromExpected` 溯源编号。
2. **原子化**：一条 `act` 只含一个 UI 动作（点击/输入/勾选/导航其一）；原文一步多动作的按顺序拆开。
3. **动作与断言分离**：`act` 指令中禁止出现验证性措辞；原文中"确认/查看/检查"类步骤译为 `assert` 或 `extract`。
4. **断言可视觉判定**：每条 `assert` 必须是看一张页面截图就能判真假的陈述，且保留原文中的具体数值/文案/元素名；无法改写成可判定形式的，放入 `manualItems` 并注明"断言不可视觉判定"。
5. **非 UI 操作识别**：数据库读写、日志检查、API 调用、抓包、断网、批处理/定时任务触发、并发构造 → 一律进 `manualItems`，给出一句原因；据此汇总 `executable`：`manualItems` 为空=full，有 manualItems 但主流程可 UI 执行=partial，全无可执行 UI 指令=manual。
6. **数据变量化**：步骤间传递的值（"记录套餐ID"后文再用）用 `extract.saveAs` + `{{var}}` 引用；字面测试数据保留原值不强行变量化。
7. **导航补全保守化**：仅当 `appBrief` 提供了页面结构时才生成导航指令；否则 `act` 使用原文名词，由 Midscene 现场定位，不编造菜单路径。
8. **输出纪律**：严格 JSON、无注释、无 markdown；`instructions` 按执行顺序排列，编号连续。

**编译结果校验（确定性代码，不靠 LLM 自觉）：** JSON schema 校验；`fromStep`/`fromExpected` 必须落在原编号范围内；`act/assert` 文本非空且 assert 不含动作动词开头；校验失败 → 自动重编译一次 → 再失败则该例降级为 A 模式并标记 `compileFailed`。

## 4. 风险

1. **编译期幻觉**（中）：LLM 可能编造原文没有的步骤或导航路径。缓解：`fromStep` 溯源 + 校验器 + 编译产物执行前可预览/可手改。
2. **非 UI 操作占比高导致 partial 泛滥**（高，已实测 38%）：套餐类用例集近半数含后端动作。产品上要把 `partial/manual` 评级如实呈现在执行报告里，否则用户会误以为"全部自动化通过"。中期可考虑给执行器加 API 动作通道（用例步骤里的"发起调用/触发结算"映射为可配置的 HTTP 动作），但这超出 Midscene 能力范围，属于执行器扩展。
3. **文本形态漂移**（低）：两种换行形态并存（95 条字面 `\n`、20 条真实换行），未来导入/手工编辑还可能引入第三种。归一化必须在编译入口做确定性处理，不能依赖 LLM 自行识别。
4. **VLM 数值断言可靠性**（中）：44% 用例带具体数值断言，"20000×0.05=1000.00元"这类需要计算的断言，aiAssert 只看截图可能判错。编译器应把"需计算"的断言改写成"账单页面显示超出部分费用为 1000.00 元"的纯比对形式。
5. **入口与数据前置依赖外部化**（高）：0% 用例含 URL，64% 前置条件是数据态。`entryUrl`、`appBrief`、数据准备（或跳过策略）必须落在项目/环境配置层，否则编译产物第一步就卡住。
6. **老用例（zentao 类）不可执行**（已知边界）：导入的粗粒手写用例编译后基本全是 manualItems——行为正确但需在 UI 上对"无可执行内容"给出明确提示，避免用户以为是工具故障。
7. **缓存失效**（低）：编译缓存键必须含用例文本 hash（title+precondition+steps+expectedResult），手工编辑用例后须自动重编，否则执行的是旧指令。
