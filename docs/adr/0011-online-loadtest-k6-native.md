# 0011 — 在线压测工具：独立 k6 工具、原生进程执行、监控可选接入

## 状态

已接受（2026-10-15，需求 grilling 会话锁定）

## 背景

NexusKit 需要一个网页化、可在线运行的压测工具。两个摆在桌面上的替代方案：

1. **增强现有「Jmeter脚本」工具**：jmeter-mcp 已具备执行能力（CONTEXT.md），看似最省事。但既有 k6 压测框架（D:\code\压力测试）的核心资产是另一套链路：k6 脚本（代码即配置，6 种执行器）+ Prometheus remote-write 实时指标 + 被测机 exporter 监控合一的报告。这条链路 2026-09 至 2026-10 在问卷系统生产环境完成过多轮真实压测验证（稳态 1600~2400 VU、尖峰 800 VU 全绿）。若走 JMeter 路线，这些已验证资产全部作废重来。
2. **执行用 Docker compose 栈**（k6 + Prometheus + Grafana，旧框架原样）：依赖 Docker Desktop 常驻，且 2026-10-14 实测 Docker 桌面版 NAT 在 2000+ VU 瞬时并发下自身成为瓶颈；同日原生 k6（Windows 单二进制）复测通过，`run-test.ps1` 的 `-Native` 开关即为该验证的产物。

## 决策

1. **新增独立「在线压测」工具（`/loadtest`，k6 引擎），不增强、不合并 Jmeter 工具**。Jmeter 工具继续走 .jmx 资产生成路线；两者的用户心智不同（JMeter 计划树资产 vs k6 脚本 + 实时监控 + 报告管线）。
2. **执行层由后端拉起原生 k6 进程**（tools/ 内置固定版本二进制），不依赖 Docker。监控可选：检测到 Prometheus 且通过三段验证（`/-/ready` 就绪 → remote-write 写入/查回 → target 健康）才接入 exporter 指标，未接入时报告只含 k6 指标并显式标注数据缺失。
3. **与旧框架资产一次性导入后独立演化**：旧框架 `projects/<name>` 目录可导入为压测项目，导入后网页版（数据库化存储）为准，不回写源目录。

## 影响

- 工具注册表新增 `loadtest_*` 系列 MCP 工具（编码代理可完成「运行 → 读报告」闭环）；页面为三页签工作区（配置 / 运行 / 历史），见 docs/prd-online-loadtest.md。
- 原生 k6 二进制纳入仓库 tools/ 并固定版本，版本升级成为显式动作；k6 v2 已删除 externally-controlled 执行器，场景构建器只暴露现存的 6 种执行器。
- 不做 Docker 模式意味着失去「一键起整套栈」的便利，换来零常驻依赖与 2000+ VU 下的可信结果；压测机自身资源曲线纳入执行页，防止压测机成为干扰项时结果被误读。
- 未来若要多压测机分布式执行，执行层接口（RunManager 串行队列 + spawn 抽象）是扩展点；本决策不排除后续补 Docker 模式，但不维护双执行路径。
